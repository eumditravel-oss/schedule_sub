# Developer Scheduler V3 — Deterministic Engine Rules

## 0. Resolved foundation rules

1. `today > task.end_date` never sets Actual to 100 and never sets completion. It sets an incomplete active Task to overdue/delayed while preserving Actual and null completion time.
2. An existing explicit 100%/completed fact remains complete. Accepted future completion sources are explicit Primary report, audited manager action, configured inspection, or migration provenance.
3. Baseline planned progress is time-phased from immutable Baseline V1. Current Actual comes from `task_actuals`/preserved explicit facts, not elapsed calendar time.
4. Project weight priority is `CONFIRMED effort → PROPOSED effort → baseline working duration → equal fallback`. Any source after CONFIRMED sets confidence `PROVISIONAL` and UI label `임시 산정`.
5. Initial proposed effort is baseline valid workdays × office daily task minutes: VN 480, KR 420. Workforce allocation percentages are excluded.
6. Office time policy is centralized: VN `Asia/Ho_Chi_Minh` 08:00–17:00; KR `Asia/Seoul` 09:00–17:00; break 60 minutes is `PROVISIONAL_CONFIG`.
7. Approval mode is `HYBRID_APPROVAL`. Cross-project conflicts use manager project priority. Primary absence requires manager-assigned temporary Primary.
8. Baseline is immutable; rebaseline approval derives from role/supervisor relationship data. No person name is authorization logic.
9. Retroactive self-edit closes at next working day 09:00 employee local; later changes use manager approval and append-only Correction Event.
10. Notifications are in-app immediate and daily manager digest, grouped per worklog Adjustment Summary. Messenger is adapter-only.
11. `TEST_SELECTOR` actor and selected view are distinct. CEO/COO write commands are rejected with 403.
12. Legacy Bootstrap is deterministic, idempotent, source `LEGACY_BOOTSTRAP`, generated by `SYSTEM_MIGRATION`, and excluded from employee worklog/attendance/overtime/digest metrics.
13. Checkpoint 2 EOD writes Actual facts only. It performs zero Baseline/Forecast date writes and creates zero schedule-adjustment events.
14. Employee input increments are 30 minutes; audited manager corrections are 15 minutes. Interval input rejects overlap, lunch intersection, invalid order, and duration mismatch.
15. Effective capacity is centralized office capacity (VN 480/KR 420) after work-calendar and deduplicated capacity events. `abs(actual-capacity) <= 30` is normal; shortage beyond 30 requires a gap reason; excess creates a pending overtime candidate.
16. Self edit closes at 09:00 on the next valid employee workday. Initial retroactive EOD is retained as `RETROACTIVE_PENDING_REVIEW`; later self revisions create a correction request rather than overwriting facts.

## 1. Engine contract

The engine calculates a forecast proposal from immutable baseline facts, accepted actual facts, explicit dependencies/constraints, and employee-minute capacity. It does not infer work from elapsed dates and does not modify the baseline.

For identical input facts, policy version, and reference cutoff, the engine must produce the same task dates, impact diff, and approval classification.

### Inputs

- current confirmed forecast version;
- affected worklog revision and accepted actual entries;
- current task actual/remaining-effort projection;
- effective-dated assignments and one Primary per task;
- employee office timezone and daily base capacity;
- country holidays, weekly profile, work overrides, leave, and capacity events;
- confirmed dependencies and constraints;
- project priority and scheduling policy;
- completed actual dates that cannot move.

### Outputs

- candidate task forecast rows;
- candidate project forecast dates;
- task/project/employee impact rows;
- approval decision and reason codes;
- new tentative or confirmed version;
- adjustment event, notification summary, and engine trace/fingerprint.

## 2. Canonical units and dates

- Effort and capacity: integer minutes.
- Stored event timestamps: UTC ISO-8601.
- Worklog business key: employee `local_work_date` plus captured IANA timezone.
- Forecast dates: local work dates (`YYYY-MM-DD`) interpreted through the assigned employee's calendar.
- One displayed workday is not a fixed calendar-day delta. It means the next eligible capacity day for the relevant assignment/calendar.
- Default daily capacity is a policy decision; proposed default is 480 minutes, not hardcoded in engine logic.

## 3. Actual fact acceptance

### 3.1 Validation order

1. Authenticate actor and authorize subject/delegation.
2. Resolve employee timezone and local work date.
3. Enforce worklog/revision/idempotency uniqueness.
4. Validate task/project/assignment links and work category.
5. Validate minute totals and category evidence.
6. Enforce progress authority: Primary or manager only.
7. Validate completion source and non-future actual date.
8. Persist worklog facts and task actual projection atomically with the adjustment request.

### 3.2 Minute validation

- Sum of normal task, meeting, outside work, company duty, training, and leave minutes may exceed base capacity only with an explicit overtime/exception reason.
- Leave minutes cannot also be task actual minutes.
- Same-project meeting minutes are project contribution but not task progress unless a task entry separately records task work.
- Other-project work is recorded against the actual project/task and consumes the employee's capacity originally available to other tasks.

### 3.3 Progress acceptance

- Primary progress is an absolute latest accepted value, not a delta to sum.
- Support progress input is stored as non-authoritative observation or rejected from the progress field.
- Progress cannot decrease without manager override/reopen reason.
- `100%` does not arise from elapsed time or minutes alone.
- Completion requires an allowed completion source. A completion event sets actual completion date and remaining effort to zero after validation.

## 4. Remaining effort policy

For task `T` at cutoff `C`:

1. Use the latest accepted Primary/manager `remaining_estimated_minutes` when present.
2. Otherwise use previous accepted remaining effort minus newly accepted task-work minutes.
3. If no prior estimate exists and `planned_effort_minutes` exists, use:

   `max(0, planned_effort_minutes × (100 - actual_progress) / 100)`

4. Migration-only fallback: estimate from current forecast working duration and approved assignment capacity. Mark confidence `ESTIMATED_DURATION_CAPACITY`.
5. Equal-weight/project-percent data cannot determine task effort. Mark `NEEDS_ESTIMATE` and prevent automatic end-date acceleration.

The engine stores the chosen source and confidence. A fallback estimate never constitutes a completion fact.

## 5. Employee capacity model

### 5.1 Daily capacity

For employee `E` and local date `D`:

`available(E,D) = base_capacity(E,D) - approved_capacity_events(E,D) - reserved_confirmed_work(E,D)`

Rules:

- Weekly off/public holiday/manual off/approved full leave: base available minutes 0.
- Work override: restores configured capacity.
- Partial leave/meeting/company duty/training: subtract exact minutes.
- Emergency leave is provisional capacity removal until approved/rejected.
- Existing actual minutes are immutable and consume historical capacity.
- Overtime is a separate approved positive capacity event, not an implicit overflow.

### 5.2 Calendar precedence

1. explicit employee work override;
2. employee leave/capacity event;
3. country manual off/public holiday;
4. weekly work profile;
5. base capacity policy.

Existing `resolveWorkDayStatusServer` remains the full-day eligibility base. V3 layers minute capacity events on top.

## 6. Dependency and constraint scheduling

### 6.1 Dependency graph

- Only `CONFIRMED` dependency rows enter the graph.
- V1 supports `FINISH_TO_START` (FS).
- Detect cycles before scheduling. A cycle returns `DEPENDENCY_CYCLE` and prevents apply.
- WBS order/date adjacency may suggest a `PROPOSED` dependency but cannot schedule it until approved.

For FS predecessor `P` and successor `S`:

`earliest(S) >= nextEligibleCapacityDate(actualOrForecastEnd(P) + lag_work_minutes)`

### 6.2 Constraint precedence

Hard constraints are applied in this order:

1. completed actual start/end (immutable);
2. `MILESTONE` instant date;
3. `FIXED_START` / `FIXED_END`;
4. `NOT_BEFORE`;
5. confirmed dependency earliest date;
6. project forecast start;
7. `AS_SOON_AS_POSSIBLE`.

If capacity/dependency cannot satisfy a hard fixed end, the engine returns a constraint violation and creates an approval-required proposal without silently changing the constraint.

## 7. Deterministic recalculation algorithm

1. **Validate worklog** and actor/subject/idempotency.
2. **Persist actual facts** and derive the latest task actual projection.
3. **Resolve remaining effort** and completion status for directly affected tasks.
4. **Select affected set**:
   - changed tasks;
   - confirmed successor subgraph;
   - tasks sharing changed employee future capacity;
   - cross-project tasks affected by that capacity under the chosen priority policy.
5. **Load current confirmed forecast** and freeze completed actual portions.
6. **Build calendars/capacity buckets** in employee-local dates at minute granularity.
7. **Topologically order dependency tasks**; independently order capacity competitors by policy.
8. **Allocate remaining effort** across eligible assigned employee capacity while respecting constraints and parallel work.
9. **Calculate task start/end** and project forecast start/end.
10. **Generate diff and reason trace** against the previous confirmed version.
11. **Classify approval** using project policy and thresholds.
12. **Persist atomically**:
    - actual/worklog revision;
    - schedule version and task rows;
    - adjustment event/impacts;
    - approval row if needed;
    - grouped notifications/outbox;
    - compare-and-swap current version pointer if confirmed.

No generic `+1 day` or `-1 day` cascade is used.

## 8. Capacity allocation and parallel work

### 8.1 Assignment allocation

- Each task has one Primary and optional Support assignments.
- Planned task effort may be allocated across assignees in minutes or percentages, but percentages only distribute effort; they do not sum progress.
- If task effort allocation is missing, Primary receives the schedulable remaining effort and Support capacity is informational until approved.
- Existing project-level allocation percentages are not used as authoritative task capacity while the workforce-weight policy remains deferred.

### 8.2 Parallel tasks

Tasks without dependency may overlap when distinct employees have capacity. Tasks sharing an employee compete for that employee's minute bucket. The engine does not serialize the whole WBS.

### 8.3 Cross-project arbitration

Recommended ordering key:

1. hard fixed/milestone urgency;
2. explicit project priority;
3. confirmed dependency criticality;
4. earliest current forecast start;
5. stable task ID as deterministic tie-breaker.

The exact project-priority policy is a required user decision. Until decided, cross-project impacts require manager approval rather than silent reallocation.

## 9. Forecast and project KPI calculations

### 9.1 Baseline planned progress as of date

For each task, compute planned consumed effort at reference date from the immutable Baseline Version. Aggregate with the task weight stored in that baseline.

### 9.2 Current actual overall progress

`sum(task_actual_progress × task_weight) / sum(task_weight)`

Weight source precedence:

1. baseline `planned_effort_minutes`;
2. baseline approved explicit task weight;
3. baseline duration × approved assignment capacity;
4. equal-weight fallback with `LOW_CONFIDENCE` marker.

### 9.3 Variances

- `progress_variance_pp = actual_overall - baseline_planned_as_of_today`
- `schedule_variance_workdays = signed employee/project calendar workday difference(baseline_end, confirmed_forecast_end)`

Calendar difference must use the configured project reporting calendar; it cannot be raw calendar days.

## 10. Approval policy

### Modes

- `AUTO_APPLY`: valid proposals become confirmed immediately.
- `HYBRID_APPROVAL`: engine classifies by thresholds.
- `ALWAYS_APPROVAL`: every proposal remains tentative until approved.

### Recommended HYBRID V1

Auto-apply only when all are true:

- every changed task moves by at most 1 workday;
- project forecast end is unchanged;
- no hard constraint or milestone is affected;
- no dependency/capacity conflict exists;
- no cross-project task changes;
- worklog is not retroactive;
- completion is not being reversed;
- source is not company duty/outside work requiring confirmation;
- no task is marked manager-critical.

Otherwise create `TENTATIVE` and `PENDING` approval. The main Gantt remains on the confirmed version; the preview shows the tentative diff.

## 11. Idempotency, transactions, and concurrency

### 11.1 Idempotency

Recommended keys:

- Morning submit: `worklog_id:revision:MORNING`
- EOD submit: `worklog_id:revision:EOD`
- Recalculate: `worklog_id:revision:engine_policy_version`
- Approval/reject/revert: command UUID unique per action

Unique constraints ensure a retry returns the existing result. The same worklog revision cannot create two adjustment correlations or apply twice.

### 11.2 Optimistic locking

Each project stores the current confirmed forecast version ID/sequence. Engine apply uses compare-and-swap semantics:

- expected parent version equals current version: apply;
- otherwise return `FORECAST_VERSION_CONFLICT`;
- reload facts and recalculate; do not patch a stale diff.

Task `schedule_revision` remains useful for legacy direct edits, but forecast version is the project-level concurrency boundary.

### 11.3 D1 transaction boundary

Use one D1 batch/transaction for facts, version rows, event/impacts, approval, notifications, and pointer update. If the affected cross-project set cannot be atomically represented in one project transaction, create one correlation with per-project proposals and require manager approval before applying projects in deterministic order.

## 12. Rollback and correction

- Worklog correction creates a new worklog revision.
- Engine recalculates from accepted facts, not by applying the inverse day delta.
- Revert creates a new confirmed forecast version whose task rows reproduce the selected previous state.
- The old version/event remains immutable and gains `reverted_at`, actor, reason, and link to the restoration event.
- Actual facts are not deleted. Incorrect facts are voided/superseded by audited correction entries.

## 13. Mandatory simulations

Assumptions for examples: reference week is 2026-08-10 through 2026-08-17; employee calendar is Monday-Friday, 480 minutes/day, with no holiday unless stated.

### CASE A — Early Primary completion

| Item | Before | 2026-08-12 EOD fact | After confirmed forecast |
|---|---|---|---|
| Task A | Forecast 08-10 → 08-13; 480 min remaining | Primary reports 100%, actual completion 08-12 | Actual end 08-12; baseline unchanged |
| FS successor B | Forecast 08-14 → 08-18, 3 workdays | Explicit FS from A | 08-13 → 08-17, at most 1 workday earlier |
| Audit | Version 5 | adjustment created | Version 6, reason `EARLY_COMPLETION` |

No unlinked task moves.

### CASE B — Full day on another project

| Item | Before 08-12 | EOD | After |
|---|---|---|---|
| Project A Task | Planned 480 min on 08-12, 480 remaining | Actual 0 min | Capacity loss causes next eligible allocation 08-13 |
| Project B Task | Unplanned/other project | Actual 480 min | Actual facts recorded on Project B |
| Employee capacity | 480 available | 480 consumed by B | 0 remaining for A on 08-12 |

Forecast is recalculated from remaining effort and future capacity; no arbitrary one-day rule is applied.

### CASE C — Same-project meeting and task work

| Item | Before | EOD | After |
|---|---|---|---|
| Meeting | none | 240 min, project linked, minutes/record supplied | project contribution 240 min |
| Task work | 480 planned; forecast end 08-13 | 240 actual, remaining estimate 240 | 240 allocated on 08-13; end remains 08-13 |
| Capacity | 480 | 240 meeting + 240 task | balanced |

The meeting does not automatically add one day and does not inflate task progress.

### CASE D — Unrelated company duty

| Item | Before 08-12 | EOD | After proposal |
|---|---|---|---|
| Capacity | 480 | `COMPANY_DUTY` 480, description required | 0 schedulable minutes |
| Planned Task | 08-12, 480 remaining | actual 0 | tentative 08-13 |
| Approval | none | company-duty impact | manager approval required |

### CASE E — Emergency leave

| Item | Before | Leave fact | After |
|---|---|---|---|
| 08-12 capacity | 480 | emergency leave 480, provisional leave link | 0 |
| Task forecast | 08-12 → 08-13 | no task actual | recalculated 08-13 → 08-14 as capacity requires |
| Evidence | normal | no meeting minutes | post-approval leave record required |

### CASE F — Primary plus two Support workers

| Entry | Minutes | Progress input | Authoritative result |
|---|---:|---:|---|
| Primary | 240 | 50% | Task actual progress 50% |
| Support 1 | 180 | observation 25% | minutes/evidence only |
| Support 2 | 120 | observation 25% | minutes/evidence only |
| Total | 540 | not 100% | Task remains 50%; employee minutes sum to 540 |

### CASE G — Early completion with NOT_BEFORE

| Item | Before | Actual | After |
|---|---|---|---|
| Predecessor | forecast end 08-14 | completes 08-12 | actual end 08-12 |
| Successor | `NOT_BEFORE 08-17` | FS would allow 08-13 | remains 08-17 |
| Slack | 0 displayed | early predecessor | 2 eligible workdays (08-13, 08-14) recorded |

### CASE H — Missing EOD worklog

| Item | 08-12 expected | Cutoff result |
|---|---|---|
| Worklog | EOD submission | status `MISSING_EOD` |
| Actual | unknown | no automatic 0 minutes/progress |
| Forecast | Version 8 confirmed | unchanged until facts/manager action |
| Notification | none | one manager missing-worklog alert/digest item |

### CASE I — Duplicate submission

| Attempt | Idempotency key | Result |
|---|---|---|
| First | `wl_123:2:EOD` | Adjustment `adj_900`, Version 9 |
| Retry | same | returns `adj_900`/Version 9; zero new rows/effects |

### CASE J — Manager revert

| Item | Before change | Changed | Revert result |
|---|---|---|---|
| Confirmed version | 10 | 11 moves Task C +2 workdays | new Version 12 reproduces Version 10 task dates |
| Audit | original event | `adj_901` | `adj_902` references `adj_901`, actor/reason stored |
| Actual facts | preserved | preserved | preserved; only forecast projection restored |

The version number remains monotonic; restore does not erase Version 11 or reset the current pointer to an old mutable row.

## 14. Engine failure/decision states

- `NEEDS_ESTIMATE`
- `NEEDS_PRIMARY`
- `DEPENDENCY_CYCLE`
- `HARD_CONSTRAINT_VIOLATION`
- `CAPACITY_DEFICIT`
- `CROSS_PROJECT_PRIORITY_REQUIRED`
- `FORECAST_VERSION_CONFLICT`
- `RETROACTIVE_APPROVAL_REQUIRED`
- `IDEMPOTENT_REPLAY`

These states produce explainable previews or approvals. None is converted into silent completion or blanket schedule movement.
